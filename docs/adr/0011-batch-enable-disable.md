# 批量 enable/disable：整批原子 + 统一 JSON 包装

`enable` / `disable` 支持一次处理多个技能（`enable <repo> <name>…`、`disable <name>…`），消除「新项目一次性装配多个技能」与「批量清理」时的机械重复。形态取可变位置参数、与彼此对称、向后兼容单技能调用；`enable <repo>`（只给 repo 不给 name）仍是用法错误，不引入隐式「启用整个 repo」。交互式选单同样支持批量（输入空格/逗号分隔的多个编号；enable 为 repo 单选 + skill 多选，disable 为多选），与非交互共用同一套原子/宽松语义。两条核心语义决策如下。

**enable 整批原子（fail-fast）**：先全量解析校验所有名字（存在性、是否歧义），再提交——任一名字无效则**整批不生效**（配置一字不写、sync 一次不跑），并**一次性列出全部失败项**（exit 1），避免用户多轮试错。`already_enabled` 是幂等成功、不阻塞；同批重复名字去重按 no-op。拒绝的替代方案是「尽力而为部分成功」：声明式配置应始终代表连贯的期望态，不该写进一半；且幂等性使「修好错字整批重跑」几乎零成本，消解了原子的主要缺点。`disable` 天然宽松——禁用未启用的名字是幂等 no-op（沿用现状的 `not_enabled`），无硬失败、无中止，逐项报告结果。整批 enable 仅在末尾跑**一次** sync（而非每个技能各跑一遍）。

**统一 `results` JSON 包装（破坏性变更）**：enable → `{"results": [{"action","skill"}, …], "sync": {…}}`（sync 整批共享一份，提到顶层）；disable → `{"results": [{"action","skill","link_removed"}, …]}`。单技能调用即 1 元素 `results`，**输出形态恒定**，脚本无需按「传了几个名字」分支解析。拒绝的替代方案是「按数量变形以兼容旧单对象输出」：输出形态随输入个数变化是公认的解析噩梦；当前处于 0.x、API 未冻结，此时做一次性 schema 收敛成本最低。退出码沿用既有 0/1/2（成功 / 域错误 / 用法错误），不新增档位——原子语义已消灭「部分成功」这一暧昧态。
